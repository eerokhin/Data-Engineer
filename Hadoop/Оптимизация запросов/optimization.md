# Impala: HASH JOIN, EXCHANGE и диагностика производительности

## 1. Как работает HASH JOIN

`HASH JOIN` --- способ соединения таблиц, при котором Impala строит
хеш-структуру по ключам одной стороны JOIN, а затем ищет в ней
совпадения для строк другой стороны.

Пример:

``` sql
SELECT
    a.user_id,
    a.object_id,
    a.report_dt,
    c.priority
FROM table_a a
LEFT JOIN table_c c
    ON a.user_id = c.user_id
   AND a.object_id = c.object_id
   AND a.report_dt = c.report_dt;
```

Упрощённо алгоритм состоит из двух этапов:

1.  **Build** --- построение хеш-структуры по ключам и необходимым
    данным одной стороны JOIN.
2.  **Probe** --- чтение строк другой стороны и поиск совпадений в
    хеш-структуре.

Хеш-структура и промежуточные данные занимают память. Объём памяти не
равен размеру исходных файлов на диске: он зависит от структуры данных,
выбранных столбцов и реализации оператора.

## 2. Что такое EXCHANGE

Impala выполняет запрос распределённо на нескольких узлах кластера.
Чтобы строки с одинаковыми ключами JOIN обрабатывались совместно, данные
могут перераспределяться между узлами по хешу ключей. Этот этап
называется **shuffle**, а соответствующая операция в плане ---
`EXCHANGE`.

Пример фрагмента плана:

``` text
EXCHANGE [HASH(a.object_id, a.user_id, a.report_dt)]
EXCHANGE [HASH(c.object_id, c.user_id, c.report_dt)]
HASH JOIN [LEFT OUTER JOIN, PARTITIONED]
```

Это означает, что обе стороны перераспределяются по ключам JOIN, после
чего выполняется соединение.

`EXCHANGE` сам по себе не является проблемой: для JOIN двух больших
таблиц это обычная стратегия. Но обмен требует сетевой пропускной
способности, времени и буферов памяти.

В `EXPLAIN` можно увидеть расположение `EXCHANGE`. В `Query Profile`
изучай доступные счётчики сетевого обмена, объём переданных данных и
время операторов. Большой объём переданных данных сам по себе ещё не
доказывает, что сеть является узким местом.

## 3. Откуда берётся spill

Во время JOIN Impala использует память для хеш-структур, буферов и
промежуточных данных. Если оператору не хватает доступной памяти, Impala
может временно записывать часть промежуточных данных на диск и позднее
читать их обратно. Это называется **spill**.

Spill может замедлять запрос, но не обязательно приводит к ошибке. Он
может возникать у разных операторов, поэтому общий показатель spill не
доказывает, что проблема находится именно в `HASH JOIN`.

### MEM_LIMIT

``` sql
SET MEM_LIMIT=10g;
```

`MEM_LIMIT` задаёт ограничение памяти для запроса на узле кластера. Это
лимит, а не объём памяти, который запрос обязательно использует. Точное
поведение зависит от конфигурации и версии Impala.

Если повышение лимита устранило spill, это означает, что дополнительного
разрешённого объёма памяти оказалось достаточно для выполнения без
прежней выгрузки данных. Но это не доказывает, что все проблемы
производительности вызваны только лимитом.

## 4. Как отличать типичные проблемы

### A. Нехватка памяти

**Что проверять:** - ненулевой `Memory Spilled`; - потребление памяти и
счётчики spill у конкретного оператора; - длительность работы оператора
и ошибки нехватки памяти.

**Что исследовать:** можно ли уменьшить объём данных до JOIN, исправить
оценки планировщика или обоснованно увеличить лимит.

### B. Дорогой сетевой обмен

**Что проверять:** - объём переданных данных; - время операций
`EXCHANGE`; - доступные показатели сетевой нагрузки и ожидания передачи
данных.

**Что исследовать:** сколько данных перераспределяется и можно ли
уменьшить объём входных данных до обмена. Сам факт наличия `EXCHANGE` не
означает плохой план.

### C. Перекос данных (data skew)

**Что проверять:** - сильно различающиеся объёмы обработанных строк
между узлами; - узлы или экземпляры операторов, которые работают заметно
дольше остальных; - различия в локальной нагрузке.

**Что исследовать:** частотность ключей JOIN. Если отдельные ключи
встречаются очень часто, данные могут распределяться неравномерно.

### D. Неточное планирование

Сравни оценки в `EXPLAIN` с фактическими показателями `Query Profile`.
Существенные расхождения в количестве строк могут указывать на
устаревшую или неточную статистику либо на неточные оценки
кардинальности.

Названия и доступность счётчиков зависят от версии Impala.

## 5. Практический порядок диагностики

1.  **Посмотреть `EXPLAIN`.** Найти `SCAN HDFS`, `EXCHANGE`,
    `HASH JOIN`, оценки количества строк и памяти.
2.  **Открыть `Query Profile`.** Проверить время, фактические объёмы
    данных, `Memory Spilled` и потребление памяти.
3.  **Исследовать `HASH JOIN`.** Уточнить, есть ли spill именно у этого
    оператора.
4.  **Исследовать `EXCHANGE`.** Оценить объём сетевого обмена и время
    передачи.
5.  **Сравнить узлы.** Проверить, не обрабатывает ли один узел
    непропорционально много данных.
6.  **Проверить статистику.** Сопоставить планируемые и фактические
    количества строк.
7.  **Менять по одному фактору.** Повторить запрос на сопоставимых
    данных и сравнить время, spill и потребление ресурсов.

## 6. Пример из практики

Для JOIN двух таблиц в Impala наблюдались:

-   около 544 млн строк в каждой таблице;
-   размеры на диске --- примерно 17 GiB на таблицу;
-   `MEM_LIMIT = 5 GiB`;
-   общий `Memory Spilled = 4.9 GiB`.

После выполнения:

``` sql
SET MEM_LIMIT=10g;
```

spill исчез.

Это полезный диагностический результат: увеличение лимита помогло
избежать прежней выгрузки данных. Для окончательного вывода нужно также
сравнить время выполнения, фактическое потребление памяти и влияние на
другие запросы кластера.

Не следует автоматически переключать такой JOIN на `BROADCAST`: таблица
размером около 17 GiB слишком велика для бездумной рассылки на каждый
узел. Стратегию JOIN нужно выбирать по плану и фактическим данным.

## Главное

-   **`HASH JOIN`** --- как Impala соединяет строки.
-   **`EXCHANGE`** --- как данные перераспределяются между узлами.
-   **`Memory Spilled`** --- объём данных, выгруженных на диск.
-   **`EXPLAIN`** --- планируемое выполнение.
-   **`Query Profile`** --- фактическое выполнение.

Оптимизация начинается с определения узкого места по измерениям, а не с
изменения настроек наугад.
