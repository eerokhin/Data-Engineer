# dbt Core — теория и архитектура

## 1. Что такое dbt

**dbt (data build tool)** — инструмент для трансформации данных внутри аналитического хранилища (DWH).

Он позволяет разрабатывать, тестировать, документировать и поддерживать SQL-преобразования в виде структурированного проекта.

Основная идея dbt:

- Данные уже загружены в хранилище.
- dbt выполняет SQL-преобразования непосредственно в DWH.
- Преобразования организованы в независимые модели.
- Зависимости между моделями формируют DAG.
- Качество данных контролируется тестами.
- Код хранится в Git и проходит через привычный процесс разработки.

dbt работает в рамках подхода **ELT (Extract, Load, Transform)**:

- **EL** — извлечение данных из источников и загрузка в хранилище.
- **T** — преобразование загруженных данных в удобные таблицы, модели и аналитические витрины.

**Важно:** dbt сам по себе не является инструментом загрузки данных из внешних систем. Для извлечения и доставки данных обычно используют Airflow, Kafka, Spark, Fivetran, Airbyte и другие инструменты.

## 2. Зачем нужен dbt

dbt особенно полезен, когда:

- В проекте много SQL-трансформаций.
- Необходимо управлять зависимостями между запросами.
- Нужна прозрачная бизнес-логика и история изменений.
- Важно контролировать качество данных.
- Необходима автоматическая документация.
- Несколько разработчиков работают над одним DWH.
- Требуется стандартизировать разработку и запуск SQL.

### Что даёт dbt

| Возможность | Польза |
|---|---|
| Models | Разделение логики на независимые модели |
| DAG | Автоматическое управление зависимостями |
| Tests | Контроль качества данных |
| Documentation | Документирование моделей и колонок |
| Lineage | Отслеживание происхождения данных |
| Git integration | История изменений и командная разработка |
| Macros | Повторное использование SQL-логики |
| Incremental models | Обработка новых и изменившихся данных |

### Почему dbt, а не просто SQL?

Обычный SQL позволяет писать любые преобразования, но сам по себе не предоставляет единого механизма управления проектом.

При использовании отдельных SQL-скриптов разработчику приходится самостоятельно:

- Определять порядок выполнения запросов.
- Управлять зависимостями.
- Организовывать тесты.
- Поддерживать документацию.
- Контролировать изменения SQL.
- Настраивать запуск всего пайплайна.

dbt добавляет надстройку над SQL:

- SQL остаётся основным языком преобразований.
- `ref()` и `source()` описывают зависимости.
- dbt автоматически строит DAG.
- Тесты проверяют качество данных.
- Документация описывает структуру хранилища.
- CLI позволяет запускать модели и тесты командами.

По сути, dbt превращает набор SQL-скриптов в структурированный и поддерживаемый проект.

## 3. Что нужно знать перед началом работы

Для работы с dbt желательно знать:

1. **SQL** — JOIN, GROUP BY, оконные функции, CTE, агрегаты.
2. **Git** — commit, branch, merge, pull request.
3. **Python** — необходим для установки и работы dbt Core.
4. **DWH** — понимание слоёв Raw, Staging, DDS, Data Marts.
5. **Основы YAML** — конфигурация проекта и описание моделей.

dbt не требует глубокого знания Python: основная работа выполняется на SQL.

## 4. ETL и ELT: место dbt в архитектуре

### ETL

1. Extract — извлечение данных.
2. Transform — преобразование данных.
3. Load — загрузка результата в хранилище.

### ELT

1. Extract — извлечение данных.
2. Load — загрузка исходных данных в хранилище.
3. Transform — преобразование данных непосредственно внутри хранилища.

### Архитектура ELT с dbt

```text
      Источники данных
   ┌────────────────────┐
   │ PostgreSQL         │
   │ REST API           │
   │ Kafka              │
   │ CSV / Parquet      │
   └─────────┬──────────┘
             │
             ▼
      Ingestion Layer
   ┌────────────────────┐
   │ Airflow            │
   │ Spark              │
   │ Kafka Connect      │
   └─────────┬──────────┘
             │
             ▼
       Data Warehouse
   ┌────────────────────┐
   │ Bronze / Raw       │
   │ Исходные данные    │
   └─────────┬──────────┘
             │
             ▼
             dbt
   ┌────────────────────┐
   │ Silver / Staging   │
   │ Очистка и типизация│
   └─────────┬──────────┘
             │
             ▼
   ┌────────────────────┐
   │ Intermediate       │
   │ Бизнес-преобразов. │
   └─────────┬──────────┘
             │
             ▼
   ┌────────────────────┐
   │ Gold / Marts       │
   │ Аналитические      │
   │ витрины            │
   └─────────┬──────────┘
             │
             ▼
       BI / ML / Analytics
```

dbt отвечает за слой Transform. Загрузка данных в Bronze обычно выполняется отдельным ingestion-процессом.

## 5. dbt Core и dbt Cloud

### dbt Core

Open-source версия dbt, которую можно запускать локально или в собственной инфраструктуре.

Особенности:

- Работа через CLI.
- SQL-модели и Jinja-шаблоны.
- Настройки через YAML.
- Подключение через адаптеры.
- Интеграция с Git.
- Возможность запускать dbt из Airflow, CI/CD и других систем.

### dbt Cloud

Коммерческая облачная платформа для работы с dbt.

Дополнительно предоставляет:

- Web IDE.
- Управление окружениями.
- Планирование запусков.
- Мониторинг выполнения.
- CI/CD-инструменты.
- Каталог и документацию данных.

В нашем проекте используется dbt Core.

## 6. Архитектура dbt Core

dbt-проект — это директория с SQL-моделями, YAML-конфигурациями, тестами и другими ресурсами.

Пример структуры:

```text
dbt/
│
├── dbt_project.yml
│
├── models/
│   ├── sources.yml
│   ├── schema.yml
│   │
│   ├── staging/
│   │   └── stg_employees.sql
│   │
│   ├── intermediate/
│   │   └── int_employee_history.sql
│   │
│   └── marts/
│       └── dm_employee_turnover.sql
│
├── tests/
│   └── assert_employee_data.sql
│
├── macros/
│   └── generate_schema_name.sql
│
├── snapshots/
│
├── seeds/
│
└── analyses/
```

Не все директории обязательны. Их наличие зависит от архитектуры проекта.

### Основные компоненты

| Компонент | Назначение |
|---|---|
| models | SQL-модели преобразования |
| tests | Пользовательские SQL-тесты |
| macros | Повторно используемые Jinja-макросы |
| snapshots | Отслеживание изменений записей во времени |
| seeds | Загрузка небольших CSV-файлов |
| analyses | Аналитические SQL-запросы |
| dbt_project.yml | Настройки проекта |

## 7. Основные YAML-файлы

### 7.1. profiles.yml

Файл подключения к хранилищу.

Обычно находится вне репозитория:

```text
~/.dbt/profiles.yml
```

Пример подключения к Trino:

```yaml
hr_dbt:
  target: dev

  outputs:
    dev:
      type: trino
      method: none
      user: hr_user
      host: localhost
      port: 8080
      database: iceberg
      schema: silver
      threads: 4
      http_scheme: http
```

Основные параметры:

| Параметр | Назначение |
|---|---|
| profile name | Имя профиля |
| target | Активное окружение |
| type | Тип адаптера |
| method | Способ аутентификации |
| host | Адрес хранилища |
| port | Порт подключения |
| database | Каталог или база данных |
| schema | Схема по умолчанию |
| threads | Количество параллельных потоков |

Один профиль может содержать несколько окружений, например `dev`, `test`, `prod`.

```yaml
hr_dbt:
  target: dev

  outputs:
    dev:
      type: trino
      host: localhost
      port: 8080
      user: dbt_user
      database: iceberg
      schema: silver
      method: none

    prod:
      type: trino
      host: trino-prod.company.local
      port: 8080
      user: dbt_user
      database: iceberg
      schema: silver
      method: none
```

Переключение окружения:

```bash
dbt run --target prod
```

`profiles.yml` может содержать логины, пароли и другие секреты, поэтому его обычно не хранят в Git.

### 7.2. dbt_project.yml

Главный конфигурационный файл проекта.

Пример:

```yaml
name: hr_dbt
version: '1.0.0'
config-version: 2

profile: hr_dbt

model-paths: ["models"]
test-paths: ["tests"]
macro-paths: ["macros"]
seed-paths: ["seeds"]
snapshot-paths: ["snapshots"]

models:
  hr_dbt:
    silver:
      +materialized: table

    gold:
      +materialized: table
```

Основные параметры:

- `name` — имя проекта.
- `profile` — профиль подключения из `profiles.yml`.
- `model-paths` — расположение SQL-моделей.
- `test-paths` — расположение тестов.
- `macro-paths` — расположение макросов.
- `materialized` — стратегия материализации моделей.

### 7.3. sources.yml

Описывает внешние по отношению к dbt модели источники данных.

Пример:

```yaml
version: 2

sources:
  - name: bronze
    database: iceberg
    schema: bronze

    tables:
      - name: employees
      - name: departments
      - name: positions
```

Использование в SQL:

```sql
SELECT *
FROM {{ source('bronze', 'employees') }}
```

Преимущества:

- Единое описание источников.
- Удобное переиспользование.
- Возможность проверять наличие и свежесть источников.
- Отображение источников в DAG и документации.

Важно: `sources.yml` описывает уже существующие таблицы, но не создаёт их.

### 7.4. schema.yml

Используется для описания моделей, колонок, документации и тестов.

Пример:

```yaml
version: 2

models:
  - name: stg_employees
    description: "Employee staging model"

    columns:
      - name: employee_id
        description: "Unique employee identifier"
        tests:
          - unique
          - not_null

      - name: employment_status
        tests:
          - not_null
          - accepted_values:
              arguments:
                values: ['active', 'terminated']
```

В dbt также можно описывать источники, snapshots и другие ресурсы в YAML-файлах.

### 7.5. .user.yml

`.user.yml` не является обязательным стандартным конфигурационным файлом dbt Core.

Не следует путать его с `profiles.yml` или `dbt_project.yml`. Назначение такого файла зависит от конкретного инструмента или расширения, которое его использует.

## 8. Модели dbt (Models)

**Model** — SQL-файл, который описывает преобразование данных.

Например:

`models/staging/stg_employees.sql`

```sql
SELECT
    employee_id,
    TRIM(first_name) AS first_name,
    TRIM(last_name) AS last_name,
    LOWER(email) AS email,
    hire_date,
    employment_status
FROM {{ source('bronze', 'employees') }}
```

Модель можно использовать как источник для другой модели.

Например:

`models/marts/dm_employee_headcount.sql`

```sql
SELECT
    employment_status,
    COUNT(DISTINCT employee_id) AS employee_count
FROM {{ ref('stg_employees') }}
GROUP BY employment_status
```

### ref()

`ref()` — специальная функция dbt для обращения к другой модели.

```sql
FROM {{ ref('stg_employees') }}
```

Она выполняет две задачи:

1. Подставляет корректное имя физической таблицы или представления.
2. Создаёт зависимость между моделями в DAG.

Не рекомендуется жёстко прописывать имена dbt-моделей в SQL, если можно использовать `ref()`.

### source()

`source()` используется для обращения к таблицам, описанным в `sources.yml`.

```sql
FROM {{ source('bronze', 'employees') }}
```

Разница:

- `source()` — обращение к внешнему источнику.
- `ref()` — обращение к другой dbt-модели.

## 9. DAG — граф зависимостей

dbt автоматически определяет зависимости между моделями через `ref()` и `source()`.

Пример:

```text
source: bronze.employees
          │
          ▼
    stg_employees
          │
          ▼
    int_employees
          │
          ├─────────────┐
          ▼             ▼
dm_headcount      dm_turnover
```

Этот граф называется DAG (Directed Acyclic Graph) — ориентированный ациклический граф.

Особенности:

- Узлы — модели, источники и другие ресурсы.
- Рёбра — зависимости.
- dbt определяет порядок выполнения.
- Независимые модели могут выполняться параллельно.
- Циклические зависимости недопустимы.

DAG можно визуализировать через:

```bash
dbt docs generate
dbt docs serve
```

## 10. Материализация моделей (Materializations)

Материализация определяет, каким физическим объектом станет SQL-модель в хранилище.

### 10.1. View

Создаётся представление (VIEW).

```sql
{{ config(materialized='view') }}

SELECT *
FROM {{ source('bronze', 'employees') }}
```

Особенности:

- Данные физически не сохраняются как отдельная таблица.
- SQL выполняется при обращении к представлению.
- Быстрое создание.
- Производительность чтения зависит от исходного запроса и СУБД.

### 10.2. Table

Создаётся физическая таблица.

```sql
{{ config(materialized='table') }}

SELECT *
FROM {{ ref('stg_employees') }}
```

Особенности:

- Результат запроса сохраняется.
- При обычном `dbt run` таблица пересоздаётся.
- Удобно для тяжёлых преобразований и аналитических витрин.

### 10.3. Incremental

Инкрементальная модель обрабатывает только новые или изменившиеся данные вместо полной пересборки.

```sql
{{
    config(
        materialized='incremental',
        unique_key='employee_id'
    )
}}

SELECT
    employee_id,
    first_name,
    last_name,
    updated_at
FROM {{ source('bronze', 'employees') }}

{% if is_incremental() %}
    WHERE updated_at > (
        SELECT COALESCE(MAX(updated_at), TIMESTAMP '1900-01-01 00:00:00')
        FROM {{ this }}
    )
{% endif %}
```

Основные понятия:

- `is_incremental()` — проверяет, выполняется ли модель в инкрементальном режиме.
- `unique_key` — ключ для сопоставления записей при поддерживаемой стратегии обновления.
- `this` — ссылка на текущую модель.

Важно: фактическая стратегия записи зависит от адаптера и конфигурации. Наличие `unique_key` само по себе не гарантирует одинаковое поведение на всех DWH.

Преимущества:

- Меньше обрабатываемых данных.
- Сокращение времени выполнения.
- Экономия вычислительных ресурсов.

При проектировании нужно учитывать поздние события, изменения старых записей, удаление данных и повторную обработку периодов.

### 10.4. Ephemeral

Модель не создаёт физическую таблицу или представление. dbt встраивает её SQL в запросы зависимых моделей через CTE.

```sql
{{ config(materialized='ephemeral') }}

SELECT *
FROM {{ source('bronze', 'employees') }}
```

Полезна для небольших промежуточных преобразований, которые не нужно сохранять отдельно.

## 11. Тестирование данных (Data Quality)

dbt позволяет проверять качество данных после выполнения преобразований.

### 11.1. Generic tests

Стандартные тесты:

| Тест | Назначение |
|---|---|
| unique | Проверка уникальности |
| not_null | Проверка отсутствия NULL |
| accepted_values | Проверка допустимых значений |
| relationships | Проверка ссылочной целостности |

Пример:

```yaml
columns:
  - name: employee_id
    tests:
      - unique
      - not_null
```

### 11.2. Singular tests

Пользовательские SQL-тесты.

Пример:

`tests/assert_no_negative_salary.sql`

```sql
SELECT *
FROM {{ ref('stg_employment_history') }}
WHERE salary < 0
```

Принцип работы:

- Если запрос вернул 0 строк — тест проходит.
- Если запрос вернул строки — тест завершается ошибкой.

Так можно проверять бизнес-правила:

- Отсутствие отрицательных зарплат.
- Корректность дат увольнения.
- Отсутствие дубликатов бизнес-ключей.
- Соответствие количества записей ожидаемым значениям.

## 12. Macros и Jinja

dbt использует Jinja — шаблонизатор, позволяющий создавать динамический SQL.

Макросы помогают переиспользовать SQL-логику.

Пример:

```sql
{% macro normalize_email(column_name) %}

    LOWER(TRIM({{ column_name }}))

{% endmacro %}
```

Использование:

```sql
SELECT
    employee_id,
    {{ normalize_email('email') }} AS email
FROM {{ source('bronze', 'employees') }}
```

Преимущества:

- Уменьшение дублирования SQL.
- Повторное использование логики.
- Генерация динамических запросов.
- Упрощение поддержки проекта.

Макросы обычно размещают в `macros/`.

## 13. Seeds и Snapshots

### Seeds

Seeds — небольшие CSV-файлы, которые dbt загружает в хранилище как таблицы.

Пример:

`seeds/department_mapping.csv`

```csv
department_id,department_group
1,Technology
2,Technology
3,Technology
4,HR
5,HR
6,Finance
```

Запуск:

```bash
dbt seed
```

Подходят для небольших справочников и таблиц соответствий.

Не рекомендуется использовать seeds для больших постоянно обновляемых наборов данных.

### Snapshots

Snapshots позволяют сохранять историю изменений записей в источнике.

Например, сотрудник меняет должность:

```text
До:
employee_id = 1001
position = Junior Data Engineer

После:
employee_id = 1001
position = Middle Data Engineer
```

Snapshot позволяет сохранить предыдущую и новую версии записи.

Это полезно для реализации историзации по принципам SCD Type 2.

Запуск:

```bash
dbt snapshot
```

Важно: snapshots требуют правильно настроенных стратегий обнаружения изменений и ключей. Они не заменяют полноценный CDC для всех сценариев.

## 14. dbt Adapter

dbt Core использует адаптеры для работы с конкретными аналитическими платформами.

Адаптер определяет, как dbt взаимодействует с конкретным SQL-движком.

Примеры:

| Адаптер | Платформа |
|---|---|
| dbt-postgres | PostgreSQL |
| dbt-trino | Trino |
| dbt-spark | Apache Spark |
| dbt-bigquery | BigQuery |
| dbt-snowflake | Snowflake |
| dbt-databricks | Databricks |

В нашем проекте:

- dbt Core — движок управления проектом.
- dbt-trino — адаптер для Trino.
- Trino — SQL-движок.
- Iceberg — табличный формат.
- MinIO — объектное хранилище.

Важно понимать: dbt не заменяет Trino. dbt генерирует и отправляет SQL, а Trino выполняет его.

| `dbt parse` | Разбор проекта и проверка структуры |
| `dbt compile` | Компиляция SQL |
| `dbt run` | Выполнение моделей |
| `dbt test` | Запуск тестов |
| `dbt build` | Сборка выбранных ресурсов с учётом зависимостей |
| `dbt seed` | Загрузка CSV |
| `dbt snapshot` | Запуск snapshots |
| `dbt docs generate` | Генерация документации |
| `dbt docs serve` | Локальный запуск документации |

### Важные различия

`dbt run` выполняет модели, но не запускает тесты.

`dbt test` запускает тесты, но не пересобирает модели.

`dbt build` выполняет выбранные поддерживаемые ресурсы проекта (например, seeds, snapshots, модели и тесты) с учётом зависимостей и порядка выполнения.

`dbt compile` генерирует SQL, но не выполняет его в хранилище.

### Полезные флаги

| Флаг | Назначение | Пример |
|---|---|---|
| `--select` (`-s`) | Выбор моделей и ресурсов | `dbt run -s stg_employees` |
| `--full-refresh` (`-f`) | Полная пересборка incremental-моделей | `dbt run -f` |
| `--debug` (`-d`) | Подробные диагностические логи | `dbt run -d` |
| `--target` (`-t`) | Выбор окружения | `dbt run -t prod` |
| `--project-dir` | Путь к проекту | `dbt run --project-dir ./dbt` |

Примеры:

```bash
# Проверить подключение
dbt debug

# Выполнить все модели
dbt run

# Выполнить конкретную модель
dbt run --select stg_employees

# Выполнить все модели Silver
dbt run --select silver

# Полностью пересобрать incremental-модели
dbt run --full-refresh

# Выполнить модели и тесты
dbt build

# Запустить тесты
dbt test

# Сгенерировать документацию
dbt docs generate

# Запустить локальный сервер документации
dbt docs serve
```

## 16. Документация и Lineage

dbt может автоматически генерировать документацию проекта.

Она содержит:

- Описание моделей.
- Описание колонок.
- Информацию об источниках.
- Зависимости между моделями.
- Результаты тестов.
- Граф происхождения данных (lineage).

Генерация:

```bash
dbt docs generate
```

Запуск локального сервера:

```bash
dbt docs serve
```

**Lineage** позволяет проследить путь данных от исходной таблицы до конечной витрины.

Например:

```text
PostgreSQL.employees
        │
        ▼
bronze.employees
        │
        ▼
stg_employees
        │
        ▼
int_employees
        │
        ▼
dm_employee_headcount
```

Это помогает понять, какие модели зависят от конкретного источника и какие витрины могут пострадать при изменении данных.

## 17. Жизненный цикл выполнения dbt

Типичный процесс разработки:

```text
       Разработчик
            │
            ▼
     Изменение SQL/YAML
            │
            ▼
        dbt parse
            │
            ▼
       dbt compile
            │
            ▼
        dbt run
            │
            ▼
     Создание моделей
            │
            ▼
        dbt test
            │
            ▼
      Проверка качества
            │
            ▼
      Результат в DWH
```

В production-процессе сборка и тестирование обычно автоматизируются через CI/CD и оркестратор.

## 18. Интеграция dbt с Airflow

В реальных проектах dbt часто запускают через оркестратор.

Например, Airflow отвечает за последовательность ETL/ELT-процессов.

```text
          Airflow DAG
               │
               ▼
       Extract from source
               │
               ▼
       Load into Bronze
               │
               ▼
          dbt build
               │
               ▼
        Silver models
               │
               ▼
          Gold models
               │
               ▼
       Уведомление о результате
```

Airflow отвечает за:

- Расписание запусков.
- Зависимости задач.
- Повторные попытки.
- Мониторинг.
- Логирование.
- Уведомления.

dbt отвечает за:

- SQL-преобразования.
- Зависимости моделей.
- Материализацию.
- Тестирование.
- Документацию.

Вместе они позволяют построить полноценный управляемый ELT-пайплайн.

## 20. Практические рекомендации

1. Разделять модели на staging, intermediate и marts.
2. Использовать `source()` для внешних источников.
3. Использовать `ref()` для связей между dbt-моделями.
4. Не хранить пароли и секреты в Git.
5. Описывать назначение моделей и колонок.
6. Добавлять тесты для ключей, обязательных полей и бизнес-правил.
7. Использовать incremental для больших таблиц, когда это оправдано.
8. Не создавать лишние физические таблицы без необходимости.
9. Хранить SQL и YAML в Git.
10. Запускать тесты после сборки моделей.
11. Использовать Airflow или другой оркестратор для управления расписанием.
12. Учитывать особенности конкретного адаптера и SQL-движка.
