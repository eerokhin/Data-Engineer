# Шпаргалка: архитектура и моделирование данных

## 1. Типы хранилищ данных

Отвечают на вопрос: **где и в каком виде храним данные?**

| Термин | Описание |
|---|---|
| **DWH (Data Warehouse)** | Аналитическое хранилище структурированных и согласованных данных |
| **Data Lake** | Хранилище данных разных форматов: CSV, JSON, Parquet, логи, изображения и др. |
| **Data Lakehouse** | Архитектура, объединяющая гибкость Data Lake с табличными форматами и возможностями аналитики DWH |

## 2. Методологии построения DWH

Отвечают на вопрос: **по каким принципам организуем корпоративное хранилище?**

| Методология | Основная идея |
|---|---|
| **Inmon** | Сначала строится централизованное корпоративное хранилище в 3NF, затем на его основе создаются аналитические витрины |
| **Kimball** | Построение хранилища вокруг бизнес-процессов с использованием фактов, измерений и согласованных размерностей |

> Inmon и Kimball — методологии построения DWH. Они определяют общие принципы организации хранилища, интеграции данных и формирования аналитических структур.

## 3. Слои данных

Отвечают на вопрос: **как организуем данные по этапам их обработки?**

Существуют разные варианты организации слоёв.

### Классическая архитектура DWH

| Слой | Назначение |
|---|---|
| **RAW** | Исходные данные, загруженные из источников с минимальными изменениями |
| **ODS (Operational Data Store)** | Операционно интегрированные данные с приведением форматов, типов, очисткой и дедупликацией |
| **DDS (Detailed Data Store)** | Детализированные интегрированные данные, подготовленные для дальнейшей аналитической обработки |
| **DM (Data Marts)** | Аналитические витрины под конкретные бизнес-задачи |

### Medallion Architecture

| Слой | Назначение |
|---|---|
| **Bronze** | Исходные данные, загруженные из источников |
| **Silver** | Очищенные, проверенные и интегрированные данные |
| **Gold** | Бизнес-модели и аналитические витрины |

Примерное соответствие:

| Классическая архитектура DWH | Medallion Architecture |
|---|---|
| RAW | Bronze |
| ODS | Silver |
| DDS | Silver / Gold |
| DM | Gold |

> Это две разные системы организации слоёв. Между ними нет строгого соответствия один к одному. В конкретном проекте слои могут объединяться, разделяться или называться иначе.

Внутри слоёв хранилища (RAW, ODS, DDS, DM или Bronze, Silver, Gold) данные могут быть организованы с использованием различных моделей: 3NF, Data Vault, Anchor Modeling, Star Schema и Snowflake Schema.

## 4. Моделирование данных

Отвечает на вопрос: **как устроены таблицы, сущности и связи между ними?**

Для моделирования данных существуют разные подходы и модели.

| Модель / подход | Основная идея |
|---|---|
| **3NF (Third Normal Form)** | Нормализованные таблицы, уменьшение избыточности данных |
| **Data Vault** | Моделирование через Hub, Link и Satellite. Подходит для интеграции данных из разных источников и сохранения истории изменений |
| **Anchor Modeling** | Моделирование через Anchor, Attribute, Tie и Knot. Позволяет гибко развивать структуру данных и хранить историю |
| **Star Schema** | Таблица фактов в центре, измерения вокруг |
| **Snowflake Schema** | Размерная модель, в которой измерения дополнительно нормализованы и разделены на связанные таблицы |

> Все перечисленные подходы относятся к одному уровню — моделированию данных. Они определяют структуру таблиц, сущностей и связей между ними.
>
> 3NF, Data Vault и Anchor Modeling часто применяются для интеграционного хранения, а Star Schema и Snowflake Schema — для аналитических витрин. Это типичные сценарии, а не обязательные ограничения.

## 5. Архитектуры обработки данных

Отвечают на вопрос: **как данные обрабатываются во времени?**

| Термин | Основная идея |
|---|---|
| **Batch Processing** | Пакетная обработка данных по расписанию или заданному условию |
| **Stream Processing** | Непрерывная обработка поступающих событий |
| **Lambda Architecture** | Два пути обработки: Batch Layer и Speed Layer |
| **Kappa Architecture** | Единый потоковый путь обработки, включая повторный расчёт по сохранённым событиям |

**1. Что такое перекос данных?**

<details>
<summary><strong>Ответ на вопрос</strong></summary>

Перекос данных (data skew) — это ситуация, когда данные распределены неравномерно, и некоторые значения встречаются намного чаще других.

Например разделили данные по какому то признаку, например по департаментам и отдали на обработку воркерам.

```text
Worker 1 → IT       → 100k строк
Worker 2 → HR       → 50k строк
Worker 3 → Finance  → 70k строк
Worker 4 → Sales    → 99.7m строк ← 🔥 
```

```text
W1 → █
W2 → █
W3 → █
W4 → █████████████████████
```

W1–W3 закончили работу и ждут W4. Хотя мы вроде бы использовали 4 workers. То есть проблема не обязательно в общем количестве данных. Проблема в том, что данные плохо распределились между исполнителями.

Это называется data skew — перекос данных.

# SCD Type 2 (Slowly Changing Dimension Type 2)

## 1. Что такое SCD2?

**SCD Type 2 (SCD2)** — это подход к хранению **истории изменений атрибутов сущности в таблицах измерений (Dimension tables)** в Data Warehouse (DWH).

При изменении атрибутов существующая запись не перезаписывается. Вместо этого:
1. Старая версия записи закрывается.
2. Создаётся новая запись с изменёнными атрибутами.
3. Для каждой версии сохраняется период её действия.

**Основная цель SCD2** — сохранять историю изменений, чтобы можно было узнать не только текущее состояние сущности, но и её состояние в прошлом.

## 2. Пример работы SCD2

Допустим, сотрудник с `employee_id = 101` работает в отделе `IT`.

Изначально таблица `dim_employee` выглядит так:

| employee_id | department | valid_from | valid_to | is_current |
|---:|---|---|---|---|
| 101 | IT | 2025-01-01 | 9999-12-31 | TRUE |

1 июля 2025 года сотрудник переходит в отдел `Analytics`.

При использовании SCD2 старая запись не удаляется и не перезаписывается. Вместо этого она закрывается, а новая версия добавляется в таблицу.

| employee_id | department | valid_from | valid_to | is_current |
|---:|---|---|---|---|
| 101 | IT | 2025-01-01 | 2025-06-30 | FALSE |
| 101 | Analytics | 2025-07-01 | 9999-12-31 | TRUE |

Теперь в таблице хранятся обе версии сотрудника.

- До 1 июля 2025 года сотрудник работал в `IT`.
- Начиная с 1 июля 2025 года сотрудник работает в `Analytics`.

## 3. Основные поля

| Поле | Назначение |
|---|---|
| `employee_id` | Бизнес-идентификатор сотрудника |
| `department` | Атрибут, изменения которого необходимо отслеживать |
| `valid_from` | Дата начала действия версии |
| `valid_to` | Дата окончания действия версии |
| `is_current` | Признак актуальной версии записи |

В качестве даты окончания текущей версии часто используют `9999-12-31`. Также могут применяться `NULL` или другие согласованные значения.

В классической модели DWH у каждой версии может быть собственный суррогатный ключ, например `employee_sk`, тогда как `employee_id` остаётся общим для всех версий сотрудника.

## 4. Как работает SCD2?

Типичный процесс загрузки данных:

1. Получаем новую запись из источника.
2. Сравниваем её атрибуты с текущей версией записи в измерении.
3. Если отслеживаемые атрибуты не изменились, новую версию не создаём.
4. Если атрибуты изменились, закрываем текущую версию.
5. Добавляем новую запись с изменёнными атрибутами и новым периодом действия.

Важно: новая версия создаётся только при изменении атрибутов, за которыми необходимо следить.

## 5. Пример SQL

Предположим, что 1 июля 2025 года сотрудник перешёл из `IT` в `Analytics`.

```sql
-- 1. Закрываем текущую версию
UPDATE dim_employee
SET
    valid_to = DATE '2025-06-30',
    is_current = FALSE
WHERE employee_id = 101
  AND is_current = TRUE;

-- 2. Создаём новую версию
INSERT INTO dim_employee (
    employee_id,
    department,
    valid_from,
    valid_to,
    is_current
)
VALUES (
    101,
    'Analytics',
    DATE '2025-07-01',
    DATE '9999-12-31',
    TRUE
);
```

Это упрощённый пример. В реальном ETL-процессе необходимо также учитывать повторные загрузки, новые сущности, дубликаты и особенности конкретной СУБД.

## 6. Получение исторических данных

Допустим, необходимо узнать, в каком отделе сотрудник работал 1 марта 2025 года.

```sql
SELECT department
FROM dim_employee
WHERE employee_id = 101
  AND DATE '2025-03-01' >= valid_from
  AND DATE '2025-03-01' <= valid_to;
```

Результат: `IT`.

Чтобы получить актуальную версию сотрудника, можно использовать условие:

```sql
SELECT *
FROM dim_employee
WHERE employee_id = 101
  AND is_current = TRUE;
```

## 7. Отличие SCD1 от SCD2

| Характеристика | SCD Type 1 | SCD Type 2 |
|---|---|---|
| Обработка изменений | Перезапись существующих значений | Создание новой версии |
| История изменений | Не сохраняется | Сохраняется |
| Количество записей на сущность | Обычно одна | Несколько |
| Использование | История не нужна | История нужна для аналитики |

## 8. Когда используется SCD2?

SCD2 применяется, когда необходимо сохранять историю изменений атрибутов сущностей, например:

- История переходов сотрудников между отделами.
- История изменения адресов клиентов.
- История изменения тарифов или категорий товаров.
- История изменения статусов и характеристик объектов.

Это позволяет строить исторические отчёты и анализировать показатели с учётом состояния измерений на определённый момент времени.

## Главное

**SCD2 — это способ хранить историю изменений, создавая новую версию записи вместо перезаписи старой.**

Старая версия сохраняется с закрытым периодом действия, а новая версия становится актуальной. Благодаря этому DWH может хранить как текущее состояние сущности, так и её историю.

# SCD (Slowly Changing Dimensions)

**SCD** — подходы к обработке изменений атрибутов измерений в Data Warehouse (DWH).

| Тип | Описание | История |
|---|---|---|
| **SCD Type 0** | Не изменяем исходное значение | Не обновляется |
| **SCD Type 1** | Перезаписываем старое значение новым | Не сохраняется |
| **SCD Type 2** | Создаём новую запись при изменении атрибутов | Полная история версий |
| **SCD Type 3** | Храним текущее и предыдущее значения в отдельных столбцах | Ограниченная история |
| **SCD Type 4** | Текущие данные храним в основной таблице, историю — в отдельной | В отдельной таблице |
| **SCD Type 6** | Комбинируем SCD1, SCD2 и SCD3 | История версий и текущие значения |

## Примеры

- **SCD1:** город клиента изменился с `Moscow` на `Berlin` — обновляем существующую запись.
- **SCD2:** создаём новую запись с городом `Berlin`, сохраняя старую запись с `Moscow`.
- **SCD3:** храним `current_city = Berlin` и `previous_city = Moscow`.

## Главное

- **SCD1** — история не нужна.
- **SCD2** — сохраняем историю изменений через новые версии записей.
- **SCD3** — сохраняем ограниченную историю в отдельных столбцах.

Для собеседования Data Engineer в первую очередь важно понимать SCD1 и SCD2.

# SCD Type 2 — пример с моим трудоустройством

## Пример

Допустим, у меня `auto_card = 123` устроился на должность Data Engineer 16.02.2025.

| auto_card | position | valid_from | valid_to |
|---:|---|---|---|
| 123 | Data Engineer | 2025-02-16 | 2199-12-31 |

`2199-12-31` — условная дата окончания, обозначающая актуальную версию записи.

## Смена должности

1 октября 2026 года я стал Senior Data Engineer.

При использовании SCD2 старую запись не удаляем, а закрываем и создаём новую версию.

| auto_card | position | valid_from | valid_to |
|---:|---|---|---|
| 123 | Data Engineer | 2025-02-16 | 2026-09-30 |
| 123 | Senior Data Engineer | 2026-10-01 | 2199-12-31 |

Теперь можно определить, на какой должности я работаю в любой из сохранённых периодов.

## Основные поля

- `auto_card` — бизнес-ключ сотрудника, общий для всех версий.
- `position` — должность сотрудника.
- `valid_from` — дата начала действия версии.
- `valid_to` — дата окончания действия версии.

У каждой версии также может быть собственный суррогатный ключ, например `employee_sk`.

## Главное

При изменении должности старая запись сохраняется с конечной датой, а новая запись получает новый период действия и условную дату окончания `2199-12-31`.

Так SCD2 позволяет хранить историю трудоустройства, не теряя предыдущие значения.

**3.Почему измерение называется медленно изменяющимся?**

<details>
<summary><strong>Ответ на вопрос</strong></summary>

Потому что `Slowly Changing Dimensions (SCD)` — это измерения, атрибуты которых меняются относительно редко, а не при каждой транзакции.

Например, клиент может годами жить в одном городе, но однажды переехать из `Moscow` в `Berlin`. Это изменение характеристики клиента, а не новая транзакция.

При этом «медленно» — условное понятие: речь о частоте изменения атрибутов измерения по сравнению с часто обновляемыми данными фактов.

Важно: `SCD2` не означает, что изменения происходят медленно. Это тип обработки изменений, при котором сохраняются исторические версии записей.

# Dimension (Измерение) в DWH

## 1. Что такое измерение?

**Измерение (Dimension)** — это таблица в DWH, которая хранит описательные характеристики объектов, используемых для анализа данных.

Примеры таблиц измерений:
- `dim_customer` — клиенты, их имена и города.
- `dim_product` — товары, их названия и категории.
- `dim_store` — магазины, их адреса и города.

## 2. Пример: факты и измерения

Допустим, Саша купил ботинки за 5 000 ₽.

**Таблица фактов `fact_sales`:**

| sale_id | customer_id | product_id | amount |
|---:|---:|---:|---:|
| 1 | 101 | 501 | 5000 |

**Таблица измерения `dim_customer`:**

| customer_id | name | city |
|---:|---|---|
| 101 | Саша | Москва |

**Таблица измерения `dim_product`:**

| product_id | product_name | category |
|---:|---|---|
| 501 | Ботинки | Обувь |

Соединяя таблицы по идентификаторам, аналитик может определить, сколько денег клиенты из Москвы потратили на обувь.

## 3. При чём здесь SCD?

Предположим, Саша переехал из Москвы в Берлин. Город — это атрибут измерения `dim_customer`.

Если необходимо сохранять историю изменений, можно использовать **SCD Type 2**.

| customer_id | name | city | valid_from | valid_to |
|---:|---|---|---|---|
| 101 | Саша | Москва | 2025-01-01 | 2026-06-30 |
| 101 | Саша | Берлин | 2026-07-01 | NULL |

Вместо перезаписи старого значения создаётся новая версия записи с новым периодом действия.

## Главное

- **Факт (Fact)** — событие или измеряемое действие, например покупка товара.
- **Измерение (Dimension)** — описание объекта, например имя клиента, город или категория товара.
- **SCD2** — способ хранить историю изменений атрибутов измерения.

## Как организовать хранение истории данных в DWH?

В первую очередь я выясню, что именно требуется хранить.

### 1. История изменений измерения (SCD2)

Если необходимо отслеживать изменения атрибутов сущности, например должности сотрудника, использую SCD Type 2.

- Новые записи добавляю.
- Если атрибуты изменились, закрываю старую версию и создаю новую.
- Для хранения периода действия использую `valid_from` и `valid_to`.

**Пример:** сотрудник сменил должность с Data Engineer на Senior Data Engineer. Обе версии остаются в таблице.

| auto_card | position | valid_from | valid_to |
|---:|---|---|---|
| 123 | Data Engineer | 2025-02-16 | 2026-09-30 |
| 123 | Senior Data Engineer | 2026-10-01 | 2199-12-31 |

### 2. История данных или событий

Если необходимо сохранять все события, каждое событие записываю отдельной строкой, не перезаписывая предыдущие.

**Пример:** Саша купил ботинки, а затем зонт.

| purchase_id | customer | product | purchased_at |
|---:|---|---|---|
| 1 | Саша | Ботинки | 2026-10-14 10:00 |
| 2 | Саша | Зонт | 2026-10-15 12:30 |

Каждая покупка — отдельное событие. По таблице можно восстановить последовательность покупок и время их совершения.

Если же источник содержит только текущее состояние и требуется хранить историю изменений всей таблицы, можно сохранять регулярные снимки данных (snapshots).

### Как выбрать подход?

- **SCD2** — история изменения атрибутов сущности.
- **Таблица событий** — история бизнес-событий.
- **Snapshot** — состояние данных на определённые моменты времени.

Выбор зависит от требований аналитика и возможностей источника данных.

# Snapshot-загрузка данных

## Что такое Snapshot?

**Snapshot — это снимок состояния данных на определённый момент времени.**

При каждой загрузке мы сохраняем текущее состояние данных, чтобы впоследствии можно было посмотреть, какими они были на конкретную дату.

## Пример

Допустим, в источнике есть таблица сотрудников.

**1 октября:**

| employee_id | name | position |
|---:|---|---|
| 1 | Алексей | Developer |
| 2 | Мария | Analyst |

Мы сохраняем снимок данных за 1 октября.

**2 октября:**

В источнике должность Алексея изменилась, а Иван появился в таблице.

| employee_id | name | position |
|---:|---|---|
| 1 | Алексей | Senior Developer |
| 2 | Мария | Analyst |
| 3 | Иван | Tester |

Мы сохраняем второй снимок за 2 октября.

## Как хранить Snapshot?

Обычно можно использовать отдельную таблицу с полем `snapshot_date`.

| snapshot_date | employee_id | name | position |
|---|---:|---|---|
| 2026-10-01 | 1 | Алексей | Developer |
| 2026-10-01 | 2 | Мария | Analyst |
| 2026-10-02 | 1 | Алексей | Senior Developer |
| 2026-10-02 | 2 | Мария | Analyst |
| 2026-10-02 | 3 | Иван | Tester |

Поле `snapshot_date` показывает, на какую дату сохранено состояние данных.

## Как происходит загрузка?

1. Получаем данные из источника.
2. Определяем дату снимка.
3. Сохраняем данные в хранилище с этой датой.
4. При следующей загрузке повторяем процесс.

Для корректной работы нужно определить, как обрабатывать повторные запуски за одну дату, удалённые записи и неполные выгрузки.

## Для чего нужен Snapshot?

- Сохранять состояние данных на разные даты.
- Анализировать, как данные менялись со временем.
- Сравнивать состояние источника между загрузками.
- Выявлять появление и исчезновение записей.

**Важно:** Snapshot сохраняет состояние данных именно в момент загрузки. Если между двумя снимками запись несколько раз менялась, промежуточные состояния не сохранятся.

Так же могут возникнуть дубли в итоговой витрине, например состояние Марии не изменилось, она как была Analyst, так и осталась.
Чтобы дублей не было, как вариант можно делать группировку по `employee_id | name | position` и брать максимальную дату `snapshot_date`

# CDC (Change Data Capture)

## 1. Что такое CDC?

**CDC (Change Data Capture)** — это подход к отслеживанию изменений в **источнике данных** и передаче этих изменений в **целевые системы (хранилище)**.

Вместо повторной загрузки всей таблицы CDC позволяет получать изменения:
- `INSERT` — добавление записи;
- `UPDATE` — изменение записи;
- `DELETE` — удаление записи.

CDC часто используется для построения инкрементальных ETL/ELT-процессов и синхронизации данных между системами.

Есть три способа захвата изменений:

1. Метка времени (например по колонке updatet_at). Например раз в час забираем строки. Удаленные строки можем не увидить. Но если строку например поменяли два раза за час, то увидим только последнее значение.
2. Тригер, при каждом изменении база сама пишет копию строки в таблицу журнала. Видно все, но каждая запись базы становится медленнее.
3. Журнал базы, любая база сначала записывает изменения в свой журнал, в постгре это например WAL. Debezium например читает этот журнал и отправляет каждое изменение (вставку, изменение, удаление) в kafka со старым и новым значением. Базу это не нагружает, поэтому в больших компаниях это стандарт. 

## 2. Пример работы CDC

Допустим, в PostgreSQL есть таблица сотрудников.

**Исходные данные:**

| id | name | salary |
|---:|---|---:|
| 1 | Иван | 100 000 |
| 2 | Анна | 120 000 |
| 3 | Пётр | 90 000 |

Зарплата Ивана изменилась, а в таблицу добавили нового сотрудника Ольгу.

**Зафиксированные изменения:**

| operation | id | name | salary |
|---|---:|---|---:|
| UPDATE | 1 | Иван | 110 000 |
| INSERT | 4 | Ольга | 95 000 |

Вместо повторного чтения всей таблицы система передаёт информацию об изменившихся записях.

## 3. Как работает CDC?

Один из распространённых вариантов — захват изменений из журнала транзакций базы данных.

Например, PostgreSQL записывает изменения в WAL (Write-Ahead Log).

Типичный CDC-пайплайн:

```text
PostgreSQL
    |
    | Изменения в WAL
    v
Debezium
    |
    | События об изменениях
    v
Kafka (topics)
    |
    | Чтение событий
    v
Consumer (Spark / Python)
    |
    v
DWH / Hadoop / ClickHouse
```

**Роли компонентов:**

- **PostgreSQL** — хранит исходные данные и журнал транзакций.
- **Debezium** — захватывает изменения в базе данных и публикует их как события, обычно через Kafka Connect.
- **Kafka** — хранит и передаёт поток событий потребителям.
- **Consumer** — читает события, обрабатывает их и применяет изменения к целевой системе.
- **DWH / ClickHouse** — целевая система, в которой поддерживается актуальное состояние данных.

CDC не обязательно работает в реальном времени: события можно обрабатывать непрерывно или пакетами.

## 4. CDC vs Full Load vs Incremental Load

| Подход | Принцип работы |
|---|---|
| Full Load | Полностью загружает таблицу |
| Incremental Load | Загружает новые или изменённые данные по заданному условию, например `updated_at` |
| CDC | Захватывает изменения в источнике, часто через журнал транзакций |

Инкрементальная загрузка и CDC могут решать похожие задачи, но отличаются способом обнаружения изменений.

Например, инкрементальная загрузка по `updated_at` может пропустить физически удалённую запись, если источник не сохраняет информацию об удалении. CDC способен передать событие `DELETE`.

При этом CDC требует настройки механизма захвата изменений и корректной обработки событий на стороне приёмника.

## 5. Зачем нужен CDC в Data Engineering?

1. **Снижение объёма обработки** — не нужно каждый раз перечитывать всю таблицу.
2. **Актуальность данных** — изменения быстрее попадают в DWH и аналитические системы.
3. **Синхронизация систем** — можно поддерживать несколько приёмников в актуальном состоянии.
4. **Обработка удалений** — можно передавать информацию об удалённых записях.
5. **Построение потоковых пайплайнов** — события можно обрабатывать с помощью Kafka, Spark и других инструментов.

## 6. Что важно учитывать?

CDC не гарантирует автоматически корректную синхронизацию данных. При построении пайплайна необходимо учитывать:

- **Порядок событий** — изменения одной записи должны применяться в правильной последовательности.
- **Повторную доставку** — событие может быть обработано несколько раз.
- **Идемпотентность** — повторная обработка события не должна приводить к некорректному результату.
- **Удаления** — необходимо корректно отражать `DELETE` в целевой системе.
- **Начальную загрузку** — нужно согласовать первоначальный снимок данных с последующими изменениями.
- **Смещение и восстановление** — после сбоя нужно продолжить чтение событий с корректной позиции.

## 7. Кратко для собеседования

**CDC (Change Data Capture)** — механизм отслеживания изменений в источнике данных, позволяющий передавать операции `INSERT`, `UPDATE` и `DELETE` в целевые системы без необходимости каждый раз перечитывать всю таблицу.

Один из распространённых способов реализации — чтение журнала транзакций БД. Например, Debezium захватывает изменения PostgreSQL и публикует события в Kafka, откуда их читает consumer и применяет к целевой витрине.

Главное различие: **Debezium захватывает изменения, Kafka хранит и передаёт события, а consumer применяет их к целевой системе.**

# Денормализованная таблица

## 1. Что такое денормализация?

**Денормализация** — это объединение данных из нескольких таблиц или дублирование значений для упрощения и ускорения чтения данных.

Денормализация часто используется в Data Engineering при построении аналитических витрин (DWH), чтобы уменьшить количество `JOIN` и ускорить выполнение аналитических запросов.

## 2. Пример

Допустим, есть две нормализованные таблицы.

**Таблица `users`**

| user_id | user_name |
|---:|---|
| 1 | Иван |
| 2 | Анна |

**Таблица `orders`**

| order_id | user_id | amount |
|---:|---:|---:|
| 101 | 1 | 500 |
| 102 | 1 | 700 |
| 103 | 2 | 300 |

Чтобы получить заказы вместе с именами пользователей, нужно выполнить `JOIN`:

```sql
SELECT
    o.order_id,
    u.user_name,
    o.amount
FROM orders o
JOIN users u
    ON o.user_id = u.user_id;
```

**Денормализованная таблица** хранит данные вместе:

| order_id | user_id | user_name | amount |
|---:|---:|---|---:|
| 101 | 1 | Иван | 500 |
| 102 | 1 | Иван | 700 |
| 103 | 2 | Анна | 300 |

Имя пользователя теперь хранится непосредственно в каждой записи заказа. Для получения имени дополнительный `JOIN` не требуется.

## 3. Зачем нужна денормализация?

- Ускорение аналитических запросов.
- Сокращение количества `JOIN`.
- Упрощение построения отчётов и витрин.
- Подготовка данных в удобном для аналитики формате.

## 4. Недостатки денормализации

- Увеличение объёма хранимых данных.
- Дублирование значений в нескольких строках.
- Необходимость обновлять зависимые записи при изменении исходных данных.
- Риск рассогласования данных.

Например, если имя пользователя изменилось, необходимо обеспечить корректное обновление имени во всех соответствующих заказах.

## 5. Нормализация vs денормализация

| Критерий | Нормализация | Денормализация |
|---|---|---|
| Хранение | Данные разделены по таблицам | Данные объединены или дублируются |
| Дублирование | Обычно меньше | Обычно больше |
| `JOIN` | Может требоваться чаще | Часто требуется реже |
| Изменение данных | Удобнее поддерживать согласованность | Нужно учитывать дублированные значения |
| Типичное применение | OLTP, операционные БД | OLAP, аналитические витрины |

## 6. Применение в Data Engineering

В аналитических хранилищах денормализация используется для подготовки данных к аналитическим запросам.

Например, в витрине продаж можно хранить:
- информацию о заказе;
- данные о клиенте;
- название товара;
- категорию товара;
- сумму продажи.

Так аналитикам не нужно каждый раз объединять множество исходных таблиц.

**Важно:** денормализация не всегда ускоряет запросы автоматически. Результат зависит от структуры данных, объёма таблиц, СУБД и характера запросов.

## Кратко для собеседования

**Денормализованная таблица** — это таблица, в которой данные объединены или продублированы ради упрощения и ускорения чтения. В Data Engineering денормализация часто применяется при построении аналитических витрин, но требует контроля согласованности данных и может увеличивать объём хранения.

## Нормальные формы в SQL

### 1NF — первая нормальная форма

**Правило:** в каждой ячейке хранится одно значение.

❌ Нарушение:

| user_id | phones |
|---:|---|
| 1 | 111, 222 |

✅ Правильно:

| user_id | phone |
|---:|---|
| 1 | 111 |
| 1 | 222 |

### 2NF — вторая нормальная форма

**Правило:** таблица находится в 1NF, и каждый неключевой атрибут зависит от всего составного ключа.

❌ Нарушение:

Ключ — `(student_id, course_id)`.

| student_id | course_id | student_name | grade |
|---:|---:|---|---:|
| 1 | 10 | Иван | 5 |
| 1 | 20 | Иван | 4 |

`student_name` зависит только от `student_id`, а не от всего составного ключа.

✅ Решение: вынести студентов в отдельную таблицу `students`, а оценки хранить в `grades`.

### 3NF — третья нормальная форма

**Правило:** таблица находится в 2NF, и неключевые атрибуты не зависят транзитивно от ключа.

❌ Нарушение:

| employee_id | department_id | department_name |
|---:|---:|---|
| 1 | 10 | IT |
| 2 | 10 | IT |

`employee_id → department_id → department_name`.

Название отдела зависит от `department_id`, а не непосредственно от ключа сотрудника.

✅ Решение: вынести отделы в таблицу `departments`.

### BCNF — нормальная форма Бойса — Кодда

**Правило:** каждый детерминант нетривиальной функциональной зависимости является суперключом.

Пример: студент может записаться к нескольким преподавателям, но у каждого преподавателя только один студент.

| student | teacher |
|---|---|
| Иван | Петров |
| Иван | Сидоров |
| Анна | Петров |

Если каждый преподаватель закреплён только за одним студентом, то `teacher → student`. Но `teacher` не является суперключом, поэтому BCNF нарушена.

### 4NF — четвёртая нормальная форма

**Правило:** отсутствуют нетривиальные многозначные зависимости, детерминант которых не является суперключом.

❌ Нарушение: у сотрудника независимо друг от друга несколько навыков и языков.

| employee | skill | language |
|---|---|---|
| Иван | Python | English |
| Иван | Python | German |
| Иван | SQL | English |
| Иван | SQL | German |

Возникают все комбинации навыков и языков.

✅ Решение: разделить данные на `employee_skills` и `employee_languages`.

### 5NF — пятая нормальная форма

**Правило:** таблицу нельзя дальше разложить без потери информации, кроме разложений, обусловленных ключами.

Пример: таблица `supplier_product_project` хранит, какой поставщик поставляет товар для проекта. Если связь полностью определяется тремя попарными отношениями — поставщик–товар, поставщик–проект и товар–проект, — таблицу можно разложить на три отношения и затем восстановить соединением без лишних строк.

**Кратко:** 1NF — одно значение в ячейке; 2NF — зависимость от всего составного ключа; 3NF — отсутствие транзитивных зависимостей; BCNF — каждый детерминант является суперключом; 4NF — многозначные зависимости; 5NF — зависимости соединения.

# DWH по Инмону (Bill Inmon)

## 1. Что это такое?

**Подход Инмона** — это методология построения хранилища данных, при которой сначала создаётся единое корпоративное хранилище данных (Enterprise Data Warehouse, EDW), а затем на его основе строятся витрины данных для отдельных бизнес-задач.

Основная идея:

> Сначала интегрируем данные всей компании в едином хранилище, затем создаём витрины для аналитики.

## 2. Общая архитектура

```text

   ИСТОЧНИКИ ДАННЫХ
┌─────────────┐ ┌─────────────┐ ┌─────────────┐
```

## 3. Пример задачи

Компания хочет анализировать встречи сотрудников.

Источники данных:

- HR-система — сотрудники и их подразделения.
- Календарь — встречи и их продолжительность.
- Финансовая система — затраты на сотрудников.

Данные находятся в разных системах. Необходимо интегрировать их в единое хранилище и предоставить аналитикам готовые витрины.

## 4. Что хранится внутри DWH?

В корпоративном хранилище данные организованы в связанные таблицы.

### Таблица employees

| employee_id | name | department_id |
|---:|---|---:|
| 101 | Иван | 10 |
| 102 | Анна | 20 |

### Таблица departments

| department_id | department_name |
|---:|---|
| 10 | Разработка |
| 20 | Аналитика |

### Таблица meetings

| meeting_id | employee_id | duration_min |
|---:|---:|---:|
| 5001 | 101 | 60 |
| 5002 | 101 | 30 |
| 5003 | 102 | 45 |

Связи между таблицами:

- `employees.department_id` → `departments.department_id`
- `meetings.employee_id` → `employees.employee_id`

Данные организованы так, чтобы информация о сотрудниках, подразделениях и встречах не дублировалась без необходимости.

В классическом подходе Инмона корпоративное хранилище обычно моделируется с использованием нормализованной модели, например третьей нормальной формы (3NF).

## 5. Как строится витрина?

Предположим, HR-команде нужна статистика встреч по каждому сотруднику.

Из корпоративного DWH создаётся витрина `mart_employee_meetings`.

```sql
SELECT
    e.employee_id,
    e.name,
    d.department_name AS department,
    COUNT(m.meeting_id) AS meetings_count,
    SUM(m.duration_min) AS total_minutes
FROM employees e
JOIN departments d
    ON e.department_id = d.department_id
LEFT JOIN meetings m
    ON e.employee_id = m.employee_id
GROUP BY
    e.employee_id,
    e.name,
    d.department_name;
```

Результат:

| employee_id | name | department | meetings_count | total_minutes |
|---:|---|---|---:|---:|
| 101 | Иван | Разработка | 2 | 90 |
| 102 | Анна | Аналитика | 1 | 45 |

Витрина содержит уже подготовленные данные, которые можно использовать для аналитики или машинного обучения.

Из того же DWH можно построить другие витрины:

- `mart_department_meetings` — статистика встреч по подразделениям.
- `mart_employee_costs` — затраты на сотрудников.
- `mart_hr_analytics` — показатели для HR-аналитики.

Все витрины используют единое корпоративное хранилище.

Ключевая особенность — **сначала корпоративное хранилище, затем витрины данных**.

# Подход Кимбалла (Kimball)

## Основная идея

**Кимбалл — это подход, при котором хранилище данных строится постепенно, начиная с отдельных витрин под конкретные бизнес-задачи.**

В отличие от подхода Инмона, мы не начинаем с проектирования единого корпоративного хранилища целиком.

Мы определяем, какие данные нужны для конкретного отчёта, находим соответствующие источники, преобразуем данные и создаём аналитическую модель — витрину данных.

Затем добавляем витрины для других бизнес-процессов. Постепенно они образуют единое аналитическое хранилище.

Важно: это не означает, что исходные данные всегда копируются напрямую в витрину без промежуточной обработки или слоёв.

## Как это работает

```text
        Источник данных
               │
               ▼
     Анализ и преобразование
               │
               ▼
       Аналитическая модель
            (витрина)
               │
               ▼
        Отчёты и аналитика
```

Например, нужно анализировать встречи сотрудников.

1. Берём данные из календаря встреч.
2. Получаем сведения о сотрудниках из HR-системы.
3. Объединяем и преобразуем данные.
4. Создаём витрину для анализа встреч.
5. Позже добавляем витрины для анализа найма, расходов и других процессов.

```text
Календарь встреч ──┐
                   ├──► Обработка ──► Витрина встреч
HR-система ────────┘

Система найма ─────────► Обработка ──► Витрина найма

Финансовая система ────► Обработка ──► Витрина расходов
```

Витрины могут использовать общие измерения, например сотрудников, подразделения и даты. Благодаря этому разные бизнес-процессы можно анализировать согласованно.

## Принцип построения

**Проектирование снизу вверх (Bottom-up)** — начинаем с отдельных бизнес-задач и постепенно расширяем хранилище.

Основные этапы:

1. **Анализ потребностей бизнеса** — определяем, какие отчёты и показатели нужны.
2. **Анализ источников** — выясняем, где находятся необходимые данные.
3. **Проектирование витрины** — определяем таблицы фактов, измерений и связи между ними.
4. **Преобразование данных** — извлекаем, очищаем и объединяем данные из источников.
5. **Создание витрины** — загружаем подготовленные данные в аналитические таблицы.
6. **Развитие хранилища** — добавляем новые витрины и согласуем общие измерения.

## Преимущества

- **Быстрый результат** — можно реализовать первую витрину, не дожидаясь проектирования всего хранилища.
- **Поэтапное развитие** — новые витрины добавляются по мере появления бизнес-задач.
- **Удобство аналитики** — таблицы фактов и измерений упрощают построение SQL-запросов и отчётов.
- **Повторное использование данных** — общие измерения позволяют согласованно анализировать разные бизнес-процессы.

## Недостатки и риски

- **Сложность интеграции новых источников** — изменения могут затрагивать несколько витрин.
- **Риск несогласованных показателей** — без единых правил расчёта одна метрика может отличаться в разных отчётах.
- **Необходимость согласования моделей** — общие измерения должны иметь единые определения и правила использования.
- **Рост сложности поддержки** — при увеличении числа витрин необходимо контролировать качество данных и зависимости между моделями.

## Главное, что нужно запомнить

**Кимбалл — начинаем с конкретной бизнес-задачи, берём данные из источников, преобразуем их и создаём витрину. Затем добавляем другие витрины и объединяем их в согласованное аналитическое хранилище.**

При этом витрины проектируются как аналитические модели на основе таблиц фактов и измерений, а общие измерения помогают согласованно анализировать разные бизнес-процессы.

# Подход Data Vault

## 1. Основная идея

**Data Vault — методология моделирования и организации данных в хранилище, который позволяет интегрировать данные из разных источников, сохранять историю изменений и отслеживать связи между сущностями.**

В отличие от Kimball, где аналитические модели строятся на основе фактов и измерений, Data Vault использует три типа таблиц: Hub, Link и Satellite.

## 2. Из чего состоит Data Vault

<img width="1312" height="1199" alt="27dd810f-7499-421b-9e00-84a5ce974cf4" src="https://github.com/user-attachments/assets/d96ae168-eefb-42f1-96fd-ae535db649e5" />

### Hub — бизнес-сущность

Хранит уникальный бизнес-идентификатор сущности, например сотрудника или встречи.

Пример `hub_employee`:

| employee_hk | employee_id |
|---|---:|
| H101 | 101 |
| H102 | 102 |

### Link — связь между сущностями

Хранит связи между бизнес-сущностями.

Например, сотрудник участвовал во встрече.

Пример `link_meeting_employee`:

| link_hk | employee_hk | meeting_hk |
|---|---|---|
| L001 | H101 | M5001 |
| L002 | H102 | M5001 |

### Satellite — атрибуты и история изменений

Хранит описательные данные сущностей и историю их изменений.

Пример `sat_employee`:

| employee_hk | department | load_date |
|---|---|---|
| H101 | Разработка | 2025-01-10 |
| H101 | Аналитика | 2026-03-01 |

В примере сотрудник перешёл из разработки в аналитику. Вместо перезаписи старого значения добавлена новая запись, поэтому история сохраняется.

## 3. Как устроено хранилище

```text
Источники данных
      │
      ▼
   Staging
      │
      ▼
   Data Vault
   ├── Hub
   ├── Link
   └── Satellite
      │
      ▼
Витрины данных
      │
      ▼
Отчёты и аналитика
```

Данные поступают из источников, проходят подготовку и загружаются в модель Data Vault. На её основе затем создаются витрины для аналитики.

## 4. Пример использования

Допустим, у компании есть HR-система и система встреч сотрудников.

- `hub_employee` хранит идентификаторы сотрудников.
- `hub_meeting` хранит идентификаторы встреч.
- `link_meeting_employee` связывает сотрудников со встречами.
- `sat_employee` хранит информацию о сотрудниках и историю её изменений.
- `sat_meeting` хранит характеристики встреч и историю их изменений.

Так можно объединять данные из разных систем и сохранять историю изменений.

## 5. Преимущества

- Сохранение истории изменений данных.
- Интеграция данных из множества источников.
- Возможность добавлять новые источники и атрибуты без перестройки всей модели.
- Возможность отслеживать связи между бизнес-сущностями.

## 6. Недостатки

- Большое количество таблиц.
- Более сложная загрузка и обработка данных.
- Для получения готовой аналитики обычно требуется дополнительное преобразование в витрины.

## Главное, что нужно запомнить

**Data Vault — это интеграционная модель хранилища, состоящая из Hub, Link и Satellite.**

- Hub — кто или что существует.
- Link — как сущности связаны между собой.
- Satellite — какие атрибуты есть у сущностей и как они менялись со временем.

## 8. Data Vault 1.0 и Data Vault 2.0

**Data Vault 1.0** — первоначальная методология построения хранилищ данных на основе Hub, Link и Satellite. Основной акцент — интеграция данных из разных источников и сохранение истории изменений.

**Data Vault 2.0** — развитие методологии, которое охватывает не только моделирование данных, но и процессы разработки, автоматизации загрузки, тестирования и эксплуатации хранилища.

### Простой пример различий

Допустим, нужно загружать данные о сотрудниках из HR-системы в Data Vault.

**Data Vault 1.0:**

1. Разработчик проектирует таблицы Hub и Satellite.
2. Пишет SQL для загрузки данных.
3. Настраивает расписание загрузки.
4. При изменении структуры источника вручную корректирует код.

**Data Vault 2.0:**

1. Разработчик проектирует ту же модель Hub и Satellite.
2. Использует стандартизированные шаблоны и, при необходимости, инструменты автоматической генерации загрузочного кода.
3. Добавляет автоматические проверки качества данных и тесты.
4. Организует развёртывание изменений и мониторинг загрузок с использованием практик CI/CD и DevOps.

Это упрощённый пример: автоматизация возможна и в Data Vault 1.0, а Data Vault 2.0 не требует обязательного использования конкретного инструмента.

### Сравнение

| Критерий | Data Vault 1.0 | Data Vault 2.0 |
|---|---|---|
| Модель данных | Hub, Link, Satellite | Hub, Link, Satellite |
| Разработка | Методология моделирования и загрузки данных | Более широкий подход к разработке и эксплуатации |
| Автоматизация | Возможна | Более выраженный акцент на автоматизации |
| Тестирование и развёртывание | Зависят от реализации | Рассматриваются в контексте современных инженерных практик |

**Главное:** Data Vault 2.0 не заменяет Hub, Link и Satellite другой моделью. Он развивает исходную методологию, уделяя больше внимания автоматизации, масштабированию и жизненному циклу хранилища.

# Anchor Modeling

**Anchor Modeling** — подход к моделированию и организации данных в хранилище (DWH), который позволяет гибко изменять структуру данных и сохранять историю изменений.

## Основные элементы

- **Anchor** — идентификаторы сущностей.
- **Attribute** — атрибуты сущностей.
- **Tie** — связи между сущностями.
- **Knot** — справочные значения.

## Пример

Вместо одной таблицы сотрудников данные разделяются на несколько таблиц:

```text
       Anchor: Employee
              |
       +------+------+
       |             |
       v             v
 Attribute: Name  Attribute: Salary

       Tie → Department
```

## Преимущества

- Гибкое добавление новых атрибутов.
- Возможность сохранять историю изменений.
- Разделение сущностей, атрибутов и связей.

## Недостатки

- Большое количество таблиц.
- Сложные SQL-запросы с множеством JOIN.

**Главное:** Anchor Modeling помогает гибко организовывать данные и сохранять историю изменений в хранилище.

# Anchor Modeling vs Data Vault

Оба подхода используются для моделирования данных в хранилищах (DWH), обеспечивают гибкость структуры и позволяют сохранять историю изменений.

## Основные отличия

| Критерий | Anchor Modeling | Data Vault |
|---|---|---|
| Основная идея | Разделение сущностей и отдельных атрибутов | Разделение бизнес-ключей, связей и атрибутов |
| Основные элементы | Anchor, Attribute, Tie, Knot | Hub, Link, Satellite |
| Хранение атрибутов | Обычно каждый атрибут хранится отдельно | Несколько атрибутов обычно группируются в Satellite |
| Основное применение | Гибкое моделирование данных с историей | Интеграция данных из разных источников с сохранением истории |

## Пример

**Data Vault:**

Сотрудник хранится в нескольких связанных таблицах.

<img width="678" height="201" alt="image" src="https://github.com/user-attachments/assets/cb77a517-c4b7-42a2-9767-c453068192f2" />

- `Hub` хранит ключ сотрудника.
- `Satellite` хранит его характеристики и историю изменений.
- `Link связывает` сотрудника с другими сущностями, например подразделением.

**Anchor Modeling:**

Информация о том же сотруднике разделяется на отдельные таблицы атрибутов.

<img width="673" height="152" alt="image" src="https://github.com/user-attachments/assets/0d09b6e1-a4f5-4152-8a48-c2bb88561f92" />

- `Anchor` хранит идентификатор сотрудника.
- Каждый `Attribute` хранит отдельное свойство: `имя`, `зарплату` или `должность`.

**В чём разница?**

Например завтра нужно добавить сотрудникам новый атрибут — дату рождения.

- В Data Vault обычно добавляют новый столбец в существующий Satellite либо создают новый Satellite — в зависимости от требований и организации модели.
- В Anchor Modeling добавляют отдельную таблицу атрибута, например `Attribute_BirthDate`.

Оба подхода позволяют хранить историю изменений. Разница — в организации таблиц.

## Главное

- **Data Vault** — Hub, Link, Satellite.
- **Anchor Modeling** — Anchor, Attribute, Tie, Knot.

**Запомнить одной фразой:** `Data Vault` группирует характеристики в `Satellite`, а `Anchor Modeling` обычно выносит каждую характеристику в отдельную таблицу.

</details>

**18. Что такое OLTP и OLAP? Чем они отличаются? Приведи соответствущие примеры баз данных.**

# Что такое OLTP и OLAP?

На верхнем уровне системы обработки данных принято разделять на два основных типа: **OLTP** и **OLAP**.

## OLTP (Online Transaction Processing)

**OLTP** — тип систем обработки данных, предназначенный для управления транзакциями в режиме реального времени.

Такие системы обрабатывают большое количество коротких транзакций: покупка товаров, внесение платежей, обновление записей, оформление заказов и т.д.

OLTP-системы оптимизированы для быстрого выполнения большого количества операций `INSERT`, `UPDATE`, `DELETE` и точечных `SELECT`.

### Что такое транзакция?

**Транзакция** — это набор операций с базой данных, выполняемых как единое целое.

Транзакция гарантирует, что все операции в её составе будут выполнены полностью и корректно либо не будут выполнены вовсе.

Это позволяет сохранять целостность данных и избегать ситуаций, когда после сбоя данные остаются в непоследовательном состоянии.

Транзакции обеспечивают соблюдение принципов **ACID**:

- **Atomicity (Атомарность)** — все операции транзакции выполняются полностью или не выполняются вовсе.  
  *Пример:* при переводе денег с одного счёта на другой деньги должны списаться с первого счёта и зачислиться на второй. Если зачисление не удалось, списание также отменяется.

- **Consistency (Согласованность)** — транзакция переводит базу данных из одного корректного состояния в другое, сохраняя установленные ограничения.  
  *Пример:* на банковском счёте не может оказаться отрицательный баланс, если такое ограничение задано в базе данных.

- **Isolation (Изолированность)** — параллельные транзакции не должны нарушать корректность выполнения друг друга.  
  *Пример:* два пользователя одновременно пытаются купить последний товар. База данных должна обеспечить корректную обработку операций, чтобы товар не был продан дважды.

- **Durability (Долговечность)** — после успешного завершения транзакции изменения сохраняются даже в случае сбоя системы.  
  *Пример:* после успешного оформления заказа и подтверждения транзакции перезапуск сервера не должен привести к потере заказа.

### Основные характеристики OLTP

- Большое количество одновременных пользователей и операций.
- Преимущественно короткие транзакции.
- Частые операции чтения и изменения данных.
- Данные обычно хранятся в нормализованном виде для уменьшения избыточности.
- Высокие требования к целостности и согласованности данных.
- Оптимизация под быстрое выполнение отдельных операций.

**Примеры СУБД:**
- PostgreSQL
- MySQL
- Oracle Database
- Microsoft SQL Server

**Пример использования:**

Интернет-магазин обрабатывает заказы клиентов в реальном времени:
1. Создаёт запись о новом заказе.
2. Добавляет товары в заказ.
3. Обновляет остатки товаров на складе.
4. Обрабатывает оплату.
5. Изменяет статус заказа.

Все операции должны выполняться корректно, поскольку ошибка может привести к потере денег или неконсистентности данных.

---

## OLAP (Online Analytical Processing)

**OLAP** — тип систем обработки данных, предназначенный для анализа больших объёмов информации.

Такие системы используются для выполнения сложных аналитических запросов: анализа трендов, построения отчётов, расчёта показателей и поддержки принятия бизнес-решений.

В отличие от OLTP, OLAP-системы оптимизированы преимущественно для чтения и аналитической обработки больших объёмов данных.

### Основные характеристики OLAP

- Работа с большими объёмами данных.
- Преимущественно аналитические запросы `SELECT`.
- Использование сложных `JOIN`, `GROUP BY`, агрегатных и оконных функций.
- Хранение исторических и детализированных данных.
- Часто используется денормализованная структура данных.
- Оптимизация под массовое чтение, сканирование и агрегацию данных.
- Данные часто поступают из нескольких операционных источников через ETL/ELT-процессы.

**Примеры OLAP-систем и СУБД:**
- ClickHouse
- Apache Impala
- Greenplum
- Amazon Redshift
- Google BigQuery
- Snowflake

**Пример использования:**

Руководитель компании анализирует продажи за последние пять лет, чтобы выявить тенденции и принять стратегические решения.

Для этого выполняются запросы:
- Анализ продаж по регионам.
- Сравнение выручки по месяцам и годам.
- Определение наиболее прибыльных товаров.
- Расчёт среднего чека.
- Анализ динамики продаж.

---

## Сравнение OLTP и OLAP

| Критерий | OLTP | OLAP |
|---|---|---|
| Назначение | Операционная обработка транзакций | Аналитическая обработка данных |
| Основная нагрузка | Чтение и изменение записей | Чтение и анализ больших объёмов |
| Операции | INSERT, UPDATE, DELETE, SELECT | Преимущественно SELECT |
| Запросы | Короткие и простые | Сложные аналитические |
| Объём данных | Обычно меньше | Обычно значительно больше |
| Структура данных | Нормализованная | Часто денормализованная |
| История данных | Обычно актуальное состояние | Часто длительная история |
| Оптимизация | Быстрое выполнение транзакций | Быстрое сканирование и агрегация |
| Примеры | PostgreSQL, MySQL, Oracle | ClickHouse, Impala, Greenplum |

## Как OLTP и OLAP взаимодействуют в архитектуре DWH?

В реальных проектах OLTP и OLAP обычно работают совместно.

Типичная архитектура:

1. **OLTP** — операционная база данных, в которой приложение создаёт и изменяет записи.
2. **ETL/ELT** — процессы извлекают данные из операционных источников и передают их в аналитическую инфраструктуру.
3. **DWH / OLAP** — данные хранятся и обрабатываются для аналитических задач.
4. **BI** — аналитики и руководители используют витрины данных для построения отчётов и дашбордов.

Таким образом, операционная система отвечает за работу приложения, а аналитическая — за обработку данных и получение бизнес-информации.

## Важные замечания

- OLTP не означает, что выборки всегда медленные. Точечные `SELECT` в OLTP-системах могут выполняться очень быстро.
- OLAP не означает, что вставка данных невозможна или всегда медленная. Скорость загрузки зависит от СУБД, формата хранения и способа загрузки.
- PostgreSQL может использоваться как для OLTP, так и для OLAP. Назначение определяется характером нагрузки и архитектурой системы, а не только выбранной СУБД.

**Главное отличие:** OLTP предназначен для быстрой и надёжной обработки операционных транзакций, OLAP — для аналитической обработки больших объёмов данных.

# Слои данных (Data Warehouse Layers)

В DWH данные обычно разделяются на логические слои в зависимости от степени их обработки и назначения.

Единого обязательного стандарта разделения на слои нет. Архитектура зависит от требований проекта, источников данных и используемых технологий.

## 1. Основные слои DWH

### RAW (Raw Data Layer)

Слой исходных данных, поступающих из различных источников.

Основная задача — сохранить данные максимально близко к оригиналу, чтобы при необходимости можно было повторить обработку.

Особенности:
- Данные сохраняются практически без изменений.
- Может сохраняться исходная структура и формат.
- Фиксируется информация о загрузке (дата, источник, идентификатор загрузки).
- Часто используется для повторной обработки данных.

Примеры источников: PostgreSQL, REST API, CSV, JSON, Kafka.

### ODS (Operational Data Store)

Слой оперативных и подготовленных данных, объединяющий информацию из операционных источников.

В зависимости от архитектуры здесь могут выполняться технические преобразования:
- Приведение типов и форматов.
- Очистка данных.
- Дедупликация.
- Унификация структуры.
- Базовые проверки качества данных.

ODS может содержать актуальное состояние операционных данных или интегрированные данные с ограниченной историей. Его назначение зависит от конкретной архитектуры.

### DDS (Detailed Data Store)

Слой детализированных и интегрированных данных. Здесь формируется основа корпоративного хранилища.

Основная задача — объединить данные из различных источников, обеспечить согласованность, историзацию и применение бизнес-правил.

На этом уровне могут использоваться различные подходы к моделированию:

- **3NF** — нормализованная реляционная модель.
- **Data Vault** — Hub, Link, Satellite.
- **Anchor Modeling** — модель, ориентированная на гибкое хранение атрибутов и истории.
- **Star Schema** — модель фактов и измерений.
- **Snowflake Schema** — размерная модель с нормализованными измерениями.

Также здесь могут формироваться Golden Records — единые согласованные записи о бизнес-сущностях, собранные из нескольких источников.

### CDM / Data Marts (Data Mart Layer)

Слой аналитических витрин, предназначенных для конкретных бизнес-задач и групп пользователей.

Основная задача — предоставить подготовленные данные для аналитики, отчётности и ML-моделей.

Особенности:
- Агрегация данных.
- Расчёт бизнес-показателей.
- Подготовка аналитических представлений.
- Денормализация при необходимости.
- Оптимизация под конкретные аналитические запросы.

Примеры:
- HR-витрины.
- Финансовые витрины.
- Витрины продаж.
- Витрины для ML-моделей.

**CDM (Corporate Data Model)** — термин, который в разных организациях может обозначать корпоративную модель данных, а не непосредственно слой витрин. Поэтому CDM и Data Marts не всегда взаимозаменяемы.

## 2. Пример архитектуры

```text
       DATA SOURCES
             |
             v
            RAW
      Исходные данные
             |
             v
            ODS
    Техническая подготовка
             |
             v
            DDS
  Интеграция и историзация
  (3NF / Data Vault / Anchor)
             |
             v
       DATA MARTS
    Аналитические витрины
             |
             v
        BI / ML / Reports
```

Это один из возможных вариантов организации DWH. В конкретном проекте некоторые слои могут отсутствовать, объединяться или иметь другие названия.

## 3. Где физически располагаются слои?

Слои не обязательно должны находиться в одной базе данных или даже в одной системе.

Например, архитектура может быть организована следующим образом:

| Слой | Технология | Назначение |
|---|---|---|
| RAW | S3 / MinIO | Исходные файлы |
| ODS | PostgreSQL | Подготовленные данные |
| DDS | Greenplum | Интегрированное хранилище |
| Data Marts | ClickHouse | Аналитические витрины |

Либо все слои могут находиться в одной Lakehouse-платформе, например на базе S3 + Iceberg + Trino.

## 4. Как физически разграничиваются слои?

Слои можно разделять на разных уровнях инфраструктуры:

- **Таблицы** — разные таблицы для каждого слоя.
- **Схемы (Schemas)** — например, `raw`, `ods`, `dds`, `cdm`.
- **Базы данных (Databases)** — отдельная БД для каждого слоя.
- **Каталоги (Catalogs)** — отдельные каталоги в Trino.
- **Директории** — отдельные префиксы или пути в объектном хранилище.

Пример организации схем в одной СУБД:

```text
database: dwh
    |
    +-- raw
    |
    +-- ods
    |
    +-- dds
    |
    +-- cdm
```

## 5. Важное отличие

**Слой данных и физический способ его разграничения — разные вещи.**

Слои — это логическое разделение данных по степени обработки и назначению.

Физически они могут быть реализованы отдельными таблицами, схемами, базами данных, каталогами или директориями — в зависимости от архитектуры платформы.

Например, `raw`, `ods`, `dds`, `cdm` могут быть четырьмя схемами в одной PostgreSQL или четырьмя отдельными каталогами в Trino.

**Главное:** архитектура DWH определяет, какие логические слои нужны проекту, а архитектура платформы определяет, как эти слои будут физически реализованы.
