# Materialized View в ClickHouse

## 1. Что такое Materialized View

**Materialized View (материализованное представление)** — это объект ClickHouse, который автоматически выполняет SQL-запрос при поступлении новых данных в исходную таблицу и записывает результат в целевую таблицу.

Materialized View позволяет автоматически выполнять преобразования данных при загрузке, без необходимости вручную запускать отдельные SQL-запросы.

Например, у нас есть исходная таблица `orders_raw`, в которую поступают JSON-сообщения. Нам необходимо извлекать из JSON отдельные поля и сохранять их в типизированную таблицу `orders_typed`.

Для этого можно использовать Materialized View.

## 2. Как работает Materialized View

Общая схема:

```text
       orders_raw
      (исходная таблица)
             |
             | INSERT новых данных
             v
     Materialized View
       (SQL-запрос)
             |
             | Преобразование данных
             v
       orders_typed
     (целевая таблица)
```

Последовательность работы:

1. В исходную таблицу поступают новые данные через INSERT.
2. ClickHouse передаёт вставленный блок данных на обработку связанной Materialized View.
3. Выполняется SQL-запрос, определённый внутри MV.
4. Полученные результаты записываются в целевую таблицу.

**Важно:** Materialized View не нужно запускать вручную. Она автоматически срабатывает при вставке новых данных в исходную таблицу.

## 3. Создание исходной таблицы

Создадим таблицу, которая будет хранить исходные JSON-сообщения:

```sql
CREATE TABLE orders_raw
(
    message String
)
ENGINE = MergeTree
ORDER BY tuple();
```

В этой таблице каждое сообщение будет храниться в виде JSON-строки.

## 4. Создание целевой таблицы

Теперь создадим таблицу для хранения обработанных данных:

```sql
CREATE TABLE orders_typed
(
    order_id UInt64,
    customer_id UInt64,
    total_amount Decimal(12, 2),
    status String
)
ENGINE = MergeTree
ORDER BY order_id;
```

Получаем две таблицы:

- `orders_raw` — хранит исходные JSON-сообщения.
- `orders_typed` — хранит извлечённые и типизированные значения.

## 5. Создание Materialized View

Создадим Materialized View, которая будет автоматически преобразовывать JSON из `orders_raw` и записывать результат в `orders_typed`.

```sql
CREATE MATERIALIZED VIEW mv_orders_raw_to_typed
TO orders_typed
AS
SELECT
    JSONExtractUInt(message, 'order_id') AS order_id,
    JSONExtractUInt(message, 'customer_id') AS customer_id,
    JSONExtract(message, 'total_amount', 'Decimal(12, 2)') AS total_amount,
    JSONExtractString(message, 'status') AS status
FROM orders_raw;
```

Разберём основные части запроса:

| Конструкция | Назначение |
|---|---|
| `CREATE MATERIALIZED VIEW` | Создаёт материализованное представление |
| `TO orders_typed` | Указывает целевую таблицу |
| `AS SELECT` | Определяет SQL-преобразование |
| `FROM orders_raw` | Указывает исходную таблицу |

В данном примере MV не хранит результат самостоятельно. Она выполняет запрос и передаёт результат в таблицу `orders_typed`.

## 6. Проверка работы Materialized View

Выполним INSERT только в исходную таблицу:

```sql
INSERT INTO orders_raw
VALUES
(
    '{"order_id":1001,"customer_id":10,"total_amount":1500.00,"status":"NEW"}'
);
```

Что произойдёт:

1. ClickHouse получает INSERT в `orders_raw`.
2. Данные записываются в исходную таблицу.
3. Автоматически срабатывает связанная Materialized View.
4. Выполняется SELECT из MV для вставленного блока.
5. JSON преобразуется в отдельные типизированные поля.
6. Результат записывается в `orders_typed`.

Проверим исходную таблицу:

```sql
SELECT *
FROM orders_raw;
```

Результат:

| message |
|---|
| `{"order_id":1001,"customer_id":10,"total_amount":1500.00,"status":"NEW"}` |

Теперь проверим целевую таблицу:

```sql
SELECT *
FROM orders_typed;
```

Результат:

| order_id | customer_id | total_amount | status |
|---:|---:|---:|---|
| 1001 | 10 | 1500.00 | NEW |

Мы выполнили INSERT только в `orders_raw`, но данные автоматически появились в `orders_typed`.

Это и есть основной принцип работы Materialized View.

## 7. Важная особенность: MV обрабатывает новые INSERT

По умолчанию Materialized View обрабатывает только новые блоки данных, которые поступают в исходную таблицу после создания представления.

Предположим, в `orders_raw` уже находилось 100 000 записей, а затем мы создали Materialized View.

Старые записи автоматически не попадут в `orders_typed`.

Если необходимо обработать существующие данные, нужно выполнить отдельный INSERT SELECT:

```sql
INSERT INTO orders_typed
SELECT
    JSONExtractUInt(message, 'order_id'),
    JSONExtractUInt(message, 'customer_id'),
    JSONExtract(message, 'total_amount', 'Decimal(12, 2)'),
    JSONExtractString(message, 'status')
FROM orders_raw;
```

Этот запрос вручную прочитает существующие записи из `orders_raw`, преобразует их и запишет результат в `orders_typed`.

Таким образом:

- Materialized View автоматически обрабатывает новые INSERT.
- Для обработки старых данных требуется отдельная загрузка.
- Создание MV само по себе не запускает полную обработку исходной таблицы.

## 8. Отличие обычного View от Materialized View

В ClickHouse существуют обычные представления (View) и материализованные представления (Materialized View).

Они отличаются принципом работы.

| Характеристика | View | Materialized View |
|---|---|---|
| Выполнение SELECT | При чтении представления | При вставке новых данных в исходную таблицу |
| Хранение результата | Не хранит отдельную копию результата | Записывает результат в целевую таблицу |
| Реакция на INSERT | Нет | Да |
| Обработка старых данных | При чтении обращается к исходным данным | Автоматически не выполняется |

**View** — это сохранённый SQL-запрос. При обращении к нему ClickHouse выполняет запрос к исходной таблице.

**Materialized View** — это механизм автоматической обработки новых вставленных данных с записью результата в целевую таблицу.

## 9. Применение Materialized View в CDC Pipeline

В нашем проекте CDC Pipeline Materialized View используются для автоматической обработки событий, поступающих из Kafka.

Общая архитектура:

```text
              Kafka
                |
                v
          orders_kafka
           (Kafka Engine)
                |
                | MV: mv_orders_kafka_to_raw
                v
          orders_cdc_raw
           (Raw JSON)
                |
                | MV: mv_orders_raw_to_typed
                v
         orders_cdc_events
         (Typed CDC Events)
                |
                | MV: mv_orders_events_to_current
                v
           orders_current
        (Current State)
```

В проекте используются три Materialized View.

### 9.1. mv_orders_kafka_to_raw

Получает сообщения из таблицы `orders_kafka`, использующей движок Kafka Engine, и сохраняет исходный JSON в `orders_cdc_raw`.

Назначение — сохранить исходные CDC-события в Raw-слое.

### 9.2. mv_orders_raw_to_typed

Читает новые JSON-сообщения из `orders_cdc_raw`, извлекает необходимые поля и записывает их в `orders_cdc_events`.

Например:

- `order_id`;
- `old_status`;
- `new_status`;
- `old_total_amount`;
- `new_total_amount`;
- `operation`;
- `event_time`;
- `lsn`.

Назначение — преобразовать исходные JSON-сообщения в структурированные CDC-события.

### 9.3. mv_orders_events_to_current

Читает новые записи из `orders_cdc_events` и формирует данные для таблицы `orders_current`.

В зависимости от типа события:

- `r` — первоначальная загрузка из Snapshot;
- `c` — создание заказа;
- `u` — изменение заказа;
- `d` — удаление заказа.

MV формирует новую версию записи, которая поступает в `orders_current`, использующую движок ReplacingMergeTree.

Назначение — поддерживать таблицу с актуальным состоянием заказов.

**Важно:** `orders_cdc_events` хранит историю CDC-событий, а `orders_current` представляет актуальное состояние сущностей. Это разные задачи хранения данных.

## 10. Особенности и ограничения Materialized View

При работе с MV необходимо учитывать несколько особенностей:

1. **Обрабатываются новые вставки.** Создание MV не означает автоматическую обработку всех ранее загруженных данных.
2. **Обработка выполняется блоками.** MV запускает запрос для вставляемого блока данных, а не обязательно для каждой строки отдельно.
3. **Результат записывается в целевую таблицу.** В нашем примере это таблица, указанная через `TO`.
4. **Изменение исходных данных не запускает MV повторно.** MV реагирует на новые INSERT, а не на произвольные изменения уже существующих строк.
5. **Ошибки обработки требуют внимания.** Нужно учитывать поведение INSERT, MV и целевой таблицы при сбоях, чтобы не допустить потери или дублирования данных.

## 11. Главное, что нужно запомнить

Materialized View в ClickHouse — это механизм автоматической обработки данных при вставке новых блоков в исходную таблицу.

Основные принципы:

- MV автоматически срабатывает при INSERT в исходную таблицу.
- SQL-запрос внутри MV выполняет преобразование данных.
- Результат записывается в целевую таблицу.
- Старые данные автоматически не обрабатываются при создании MV.
- MV позволяет строить последовательные этапы обработки данных внутри ClickHouse.

**Применительно к CDC:** Materialized View выступают в роли автоматических этапов обработки потока событий — от получения JSON из Kafka до формирования типизированной истории изменений и таблицы актуального состояния.
